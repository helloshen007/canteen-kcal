# 项目文档说明

> 配套仓库:https://github.com/helloshen007/canteen-kcal

## 一、项目简介

**问题**:给一张食堂餐盘的俯拍照片,输出盘中有哪些食材、各多少克、合计多少千卡。

**数据**:Nutrition5k(Google, CVPR 2021)子集,60 张图,40 张标定 / 20 张测试,按时间连续块划分(相邻编号常是同一盘菜的增量扫描,随机划分会污染测试集)。

**两种方案,同一组输入**:

- **方案 A(传统)**:YOLO-World 开放词汇检测 → 跨类别 NMS → SAM 框提示分割 → 同类掩膜并集 → 标定集拟合"像素→克数"系数 → 查营养表。
- **方案 B(多模态大模型)**:让大模型只输出"食材名 + 克数",名称限定在同一个 23 种食材的封闭词表内,热量用**和方案 A 同一张营养表**计算。

这样两个方案比的只是"认得准不准、分量估得准不准",没有别的变量。

**主要结果**(完整表格见 `docs/results.md`):

| 方案 | 菜名F1 | 热量MAE(kcal) | 基线MAE(kcal) |
|---|---|---|---|
| A YOLO-World+SAM | 0.25 | 61.55 | 72.64 |
| B 多模态大模型 | 0.82 | 27.72 | 72.64 |

大模型菜名识别明显更准,热量误差也更小;但两者都有同一个毛病——**重量估不准**。方案 A 是"几乎认不出",方案 B 是"认得准但称得粗"。

**怎么跑**:见 README 的「复现」一节。

## 二、个人感悟

**1. 环境这一步最磨人,也最不该省。**
虚拟环境一开始建在了 `C:\Users\lenovo`,终端不在项目目录里,`requirements.txt` 根本找不到;清华镜像里 `ultralytics` 一开始也没拉到可用版本。这些坑本身不难,难的是报错看不懂时容易怀疑"是不是我电脑不行"。后来发现,先确认"我在哪个目录、用的哪个 python",能省掉一半的排查时间。

**2. 数据的问题往往藏在"看起来只有图"里。**
从 HuggingFace 下载的版本一开始只打印出 `image_id`,我以为这个数据集不提供真值,差点改成纯演示。后来在截图里发现仓库还有 `metadata.jsonl`——真值一直都在,只是我脚本没去读它。这件事之后我养成了习惯:先 `ls` 一遍,再判断"有没有"。

**3. 密钥这一关,和算法无关,但一样卡人。**
阿里云百炼要实名,流程走到一半放弃,最后换成 DeepSeek。中间还遇到两个纯工程问题:一个是 `.env` 只在自测脚本里被读取,批量脚本读不到环境变量,于是拿 DeepSeek 的密钥去问了 Anthropic 的接口;另一个是模型默认开思考模式,推理 token 吃满了 `max_tokens`,返回的正文是空的。这两个问题都不是"模型不行",而是"我没把配置和调用看清楚"。

**4. 结果和直觉不一样,但更可信。**
我原本以为 YOLO + SAM 至少能框出个大概。实际是:置信度阈值 0.30 时,20 张测试图里 19 张一个食材都没检出;降到 0.05 才有 F1=0.25,热量误差也只比"不看图直接猜平均值"好一点点。反而是大模型,在单一食材的图上做到了 P=R=F1=1.00。这让我第一次直观感受到:开放词汇检测对小目标、外观相近的物体,确实不够用。

**5. 关于 AI 辅助开发。**
这个项目大量用了 AI 辅助:写脚本、排查报错、甚至读官方文档确认模型名。但有几个地方必须自己判断——比如"阈值 0.05 是在测试集上比较后选的",严格来说应该在标定集上定完再冻结,这是方法学瑕疵,AI 不一定会主动指出;再比如"这个结果到底说明什么",只能自己对着数字想。我的体会是:AI 能把"实现"这一步压缩得很短,但"这个实验设计得对不对"仍然得自己负责。

**6. 如果继续做。**
一是把重量估计单独拿出来做(比如加一个参照物,或者用深度/尺寸先验),现在两个方案的分量误差都偏大;二是把词表从中式食堂的菜名重建,23 种美式食材离真实使用场景还远;三是阈值选择改到标定集上做,避免测试集泄漏。
